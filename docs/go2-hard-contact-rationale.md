# Go2 为什么要用硬接触训练 —— 一份可复现的诊断记录

> 结论先行: **软接触 (condim=3 + solimp 宽度 0.023 + warp 2 次迭代) 训练出来的 33M 策略,
> 在训练物理里中位存活 662 步, 在 CPU MuJoCo(100/50) 里只有 128 步 —— 5.2 倍的 sim-to-sim gap。**
> 也就是说"训练时看着还行"的那个指标, 描述的不是部署时跑的那套物理。
> 所以 v2 把足端接触改成**与部署模型逐项一致**的硬接触, 让训练物理 == 评测物理 == 部署物理。

---

## 1. 问题是怎么暴露的

Go2 v1 (软接触, 40M 计划) 跑到 33M 时被一次 CUDA OOM 打断 (评测进程与训练抢显存)。
用落盘的 33M 检查点做三组评测, 结果自相矛盾:

| 评测 | vx (cmd 0.5) | 存活 | 中位倒下时间 |
|---|---|---|---|
| 平地, CPU MuJoCo 100/50 | **+0.539** (误差 0.083) | **100%** | 15.0 s (跑满) |
| 地形, CPU MuJoCo 100/50, 原点出生 | +0.208 | 12.5% | 2.14 s |
| 地形, CPU MuJoCo 100/50, 随机出生 | +0.163 | 0% | 2.87 s |
| 地形, **warp (训练物理)**, 原点出生 | **+0.502** | 6.2% | **13.2 s** |

前两行说"平地完美、地形不行"; 最后一行说"在训练物理里, 地形上速度跟踪分毫不差
(0.502 vs 指令 0.500), 而且能活 13 秒"。这两件事不可能同时为真 —— 除非
**评测用的物理和训练用的物理不是同一套**。

复现 (两个都只用 CPU, 不占 GPU):
```bash
cd mjx-go1-getup
CKPT=models/go2_v1_logs/checkpoints/000033030144

# 训练物理 (warp): 32 环境 × 750 步, 原点出生, 固定指令 0.5
XLA_PYTHON_CLIENT_PREALLOCATE=false XLA_PYTHON_CLIENT_MEM_FRACTION=0.35 \
  python sim/probe_go2_warp_eval.py --policy $CKPT --envs 32 --steps 750 \
  --spawn origin --cmd 0.5 0 0

# 评测物理 (CPU MuJoCo 100/50): 16 轮 × 15 s
JAX_PLATFORMS=cpu python sim/eval_go2.py --policy $CKPT --terrain terrain \
  --cmd 0.5 0 0 --seeds 16 --duration 15
```

## 2. 排除掉的可能原因

**(a) 评测脚本的 35 维高度扫描算错了?** 不是。把 `eval_go2.Go2Sim.terrain_height`
与引擎真值 `mj_ray` 在 400 个随机点上对拍:

```
n=400/400  eval_go2 vs engine mj_ray: max=0.00276 m  p99=0.00082 m  median=0.000000
```

最大 2.8 mm、中位 0 —— 采样正确。地形高度不是问题来源。

**(b) 观测/动作顺序错位?** 不是。parity-smith 的接口互检在同一个物理状态下比 91 维 obs,
`max|Δobs| = 0.000e+00` 逐段全 0。

**(c) 策略本身不会走路?** 不是。平地上 16/16 轮跑满 15 s, vx 0.539 (指令 0.5),
跟踪误差 0.083 m/s, 足端滑移 0.51 m/s, 关节超软限位 1.1%。平地行走是合格的。

## 3. 真正的两个原因

### 3.1 训练物理与评测物理不等价 (主因)

Go1 的 `envs/go1_walk.py` 头部写得很明白, 而且有实测支撑:

- 默认档 (软接触) 在 MJX 迭代求解器下用 **2 次迭代**;
- **硬接触档实测与 CPU 参照逐位一致** (`diag_hard_contact.py`: iterations=20 与 100
  的沉降 z / 残差 / 6s 随机动作结果逐位相同)。

我们 v1 用的是软接触 + 2 次迭代。`sim/eval_go2.py` 的 `--solver soft` 档 (=2/5) 在
CPU 上甚至**直接发散** (parity-smith 实测: 8.28 s QACC NaN, 倾角 173°), 也就是说
训练用的那套接触参数在 CPU 上根本不可复现。策略于是在 warp 的接触模型里学出一套
步态, 换到 CPU 的接触模型就散架 —— 地形越复杂、接触越频繁, 差异被放得越大
(平地差异 1.5x, 地形差异 5.2x)。

### 3.2 策略在地形上确实还不够稳 (次因, 不能全赖物理)

即便在训练物理里, 中位也只活 662/750 步。vx 跟踪是完美的 (0.502), 说明它会走,
是"走一阵然后被地形绊倒"。这一条只能靠更多训练步数 + 更难的分布来修。

## 4. v2 的做法

1. **足端接触改成与部署模型逐项一致** (`models/go2/go2_mjx_position.xml` 的 `class="foot"`):
   `condim=6`, 不写 `solimp` (取 MuJoCo 默认 `0.9/0.95/0.001/0.5/2.0`),
   `friction="0.4 0.02 0.01"`, `priority=1` —— 与
   `mjx-go2-mujoco2ros2/models/go2/go2.xml` 完全相同。
   训练时用 `--hard_contact` (env 会把 solver iterations 提到 20/10, 并且**不再覆盖**足端参数)。
2. 其余配方逐位不变 (地形 / 高度扫描 / 推挤 / 观测噪声 / 步态相位 / ascent / symmetry),
   这样 v1 → v2 是**单变量对比**。
3. 训练期间**不再跑任何占 GPU 的评测** —— 上一次崩溃的直接原因就是这个。
   要评测就用 `JAX_PLATFORMS=cpu`。

## 5. 这套改动带来的一个额外好处

训练物理 = 评测物理之后, "训练日志里的 eval_reward" 才第一次**真的是**在描述我们要交付的东西。
在此之前, 拿训练 eval 曲线去判断模型好坏, 判断的是另一个仿真器里的另一个机器人。

## 6. 残留风险 (诚实标注)

- `margin`: 训练 XML 全 0 (warp MULTICCD 硬性要求), 部署 XML 是 0.001。
  parity-smith 实测这一项单独贡献最小 (漂移只降 15.4%), 且不影响静态站姿。
- 训练用 warp 的 20/10 次迭代, 部署 CPU MuJoCo 用 100/50。Go1 实测两者逐位一致,
  但那是 Go1 的模型; Go2 的 20/10 与 100/50 是否逐位一致, **还没有在本机复测过**。
  这是一条明确的待办 (见 docs/go2-status.md)。
