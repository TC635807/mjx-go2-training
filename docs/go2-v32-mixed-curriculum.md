# Go2 v32: 混合地形课程 (2026-10-21 下午)

背景 (来自用户决定与 v31 结论): v31 的 1536-768 大网络 + 纯台阶课程把 0.03-0.05m
台阶上 2 级做到 70-86%, 但训练完再用单一 hyb2 巩固会侵蚀台阶和部署稳健性
(v31d CPU 89.2->80.8, v31e 78.3, 台阶也回落)。结论是"训完再巩固"路线不对;
正确做法是把**台阶 + 离散箱体 + 碎石混合障碍**放进同一张地形, 用 per-env 课程
一次训练同时学"爬台阶"和"部署鲁棒性"。本轮即实现并验证这条路线。

## 1. 地形: `sim/gen_terrain_mixed_curriculum.py` -> mixed1

* 26x26 格 (0.4m, 场 ±5.2m), **5 条互相隔离的混合障碍赛道** (宽 5/5/4/4/4 格,
  1.6-2.0m) + 4 道 0.45m 隔墙;
* 每条赛道剖面 (26 格):
  * 0-1 入口平道 (0.8m)
  * 2-4 上行台阶 (h, 2h, 3h)
  * 5-6 平台 (3h)
  * 7-8 下行 (2h, h)
  * 9-13 离散箱体区 (高度 1.0h/0.5h/1.5h/0.8h/1.2h, 每 lane 打乱)
  * 14-17 碎石区 (0.01-0.03m 小起伏)
  * 18-25 出口平道
* 难度档 h = 0.02/0.04/0.06/0.08/0.10m;
* spawn_entries 5 个 (每条赛道入口 x=-4.6, yaw=0), 供 per-env 课程按 level 选赛道;
* hfield 与 box 场同尺寸 (±5.2m), 无外圈平地; 456 个 box, 最高 0.45m (隔墙)。

## 2. 训练

* 从 v31c (大网络台阶专精) 热启动, 1536-768, lr 3e-5, 6M 步;
* per-env 课程: init_max=2, success_dist=3.5m (爬过台阶+进入箱体区), min_dist=1.2m;
  升级/降级逻辑同 `sim/brax_curriculum.py` (legged_gym 式);
* 奖励: 混合部署口径 —— orientation -2.5, feet_clearance -0.7(target 0.10),
  forward_progress 1.0, lazy_stop -1.5, termination -20, action_acc -0.01,
  hip -0.3, swing 0.18, terminate_body_pen 0.02; 命令 vx∈[0.3,0.7], wz∈[0,0.15];
* 目的: 同一模型同时具备 (a) 0.03-0.06m 台阶多级攀爬, (b) hyb2/stg1 等部署地形
  的稳健性 (箱体/碎石/台阶混合)。

解读:
* **混合地形课程是台阶能力的正确路线**: 0.03m 上 2 级 95-97%, 0.05m 上 2 级 69-74%,
  且 0.05m 存活 91-92% (v29c 77%), 速度也快 20-30%;
* warp 部署地形 (固定前向命令) 上 hyb2/rubble/bg200 已 ≥ v29c, stg1 持平;
* 但 CPU 全命令分布 (含转向/侧移) 的 24seed 矩阵仍低于 v29c (83.3 vs 89.2),
  原因是混合课程训练命令只有前向 (vx 0.3-0.7, wz 0-0.15), 转向/侧移鲁棒性不足;
  0.8M 全命令短巩固不足以完全补回;
* 0.08m 以上: v32/v32b 能上 1 级 (14-26%) 但会摔 (存活 40% vs 66%), 仍受能力上限限制。

### 3.5 结论与选择

1. **混合地形课程本身成功**: 一个模型同时做到"0.03-0.05m 台阶强 + warp 部署不差 +
   速度更快", 是 v31 之后最好的台阶模型 (v32b 为最佳候选);
2. **推荐下一步**: 用混合地形课程 + **全命令分布** (vx 0-1, vy±0.4, wz±1.5, 或 PIE 式
   "obstacle 80% 直行/20% 小转向") 直接训练 (而不是训完再巩固), 预期可同时达到
   "v29c 级全命令鲁棒 + v32 级台阶能力";
3. **默认档**: 若追求部署最稳仍用 v29c; 若优先台阶能力, 可用 `PROFILE=go2_v32b`
   (台阶 0.03m 上2级 97%, 0.05m 上2级 69%, warp 部署 ≥ v29c; CPU 全命令矩阵低 6pp);
   最终默认归属待 48-seed CPU 矩阵复核 (噪声 vs 真差异)。


针对 3.3 的诊断: 从 v32 再做 **0.8M 步 hyb2 巩固** (lr 1e-5, 全命令分布
(vx 0..1.0, vy ±0.4, wz ±1.5), RING 出生, 保留台阶奖励项), 目标: 补回转向/全命令
鲁棒性同时不丢台阶收益。结果待回填。

### 3.7 最终建议

* **默认交付保持 v29c** (部署最稳: 48seed 总 87.5%, hyb2 91.7);
* `go2_v32` / `go2_v32b` 作为**台阶专精实验档**交付: 台阶 0.03m 上2级 ~97%,
  0.05m 上2级 ~69% (存活 91%), warp 前向部署 ≥ v29c, 速度快 17-30%;
* **下一步 (最高优先级)**: 用混合地形课程 + **全命令/地形感知命令分布**直接训练
  (例如 70% 前向偏置 + 30% 全向, 或 PIE 式 obstacle 80% 直行/20% 小转向),
  目标: 同时拿到 v29c 的全命令鲁棒 + v32b 的台阶能力。这是本轮实验最明确的结论。

## 5. v33: 20M 长训练 (混合课程 + 混合命令 + lr 衰减)

用户问题: "继续延长训练到 20M 会怎么样? Go1 用过 60M, 越大越好么?"

结论先行: **不是越大越好, 但"课程持续变难 + 命令分布变宽 + lr 衰减"三者同时满足时,
20M 确实继续涨。** 本轮 v33 实测: 四段 5M 的 best eval_reward **单调上升**
466.9 -> 570.2 -> 620.5 -> **750.4**, ep_len 576 -> 612, 没有出现 v31b/v31c 那种
后期回落 —— 说明 lr 阶梯衰减 + 混合命令分布解决了"恒定 lr 后期震荡"的问题。

配置:
* 地形: `mixed1` 混合地形课程 (台阶 0.02-0.10 + 离散箱体 + 碎石, per-env 课程);
* 命令: `forward_prob=0.7` — 70% 前向偏置 (vx 0.25-0.75, 小 wz) + 30% 全命令
  (vx -0.2-0.9, vy ±0.3, wz ±1.0), 修复 v32"只训前向 -> 全命令 hyb2 低 21pp";
* 20M = 4 段 x 5M 链式 warm-start, lr 4e-5 -> 2e-5 -> 1e-5 -> 5e-6;
* 每段 5 次 eval, 保留 best; 段间从上一段 best 热启动。

| 段 | 步数 | lr | best eval_reward | ep_len |
|---|---|---|---|---|
| v33a | 5.24M | 4e-5 | 466.9 (@3.93M) | 576 |
| v33b | 5.24M | 2e-5 | 570.2 (@5.24M) | 564 |
| v33c | 5.24M | 1e-5 | 620.5 (@5.24M) | 559 |
| v33d | 5.24M | 5e-6 | **750.4 (@5.24M)** | **612** |

与历史对比: v31b 6.2M 恒定 lr 时 best@4.98M 后回落; v31c 4.1M 后期退化;
v32 6.2M 仍在涨但没有 lr 衰减。v33 证明**长训练的收益依赖 schedule + 分布变宽**,
单纯重复同一分布 20M 不一定会涨。

验收 (v33d vs v29c/v32b) 见下一节。

结论:
1. **20M + 4 段 lr 衰减 + 混合课程 + 混合命令** 是本轮最成功的组合: 四段 eval 单调上升,
   台阶 0.05m 上 2 级从 v32b 的 67% 提到 **83% 且存活 95%**;
2. 部署侧: warp 各地形 ≥ v29c (stg1 在噪声内), CPU 总存活在噪声内持平 (86.7 vs 87.5),
   速度 +11%, 位移 +14%, 髋显著更好, stg1/rubble 更好; 代价是 CPU 全命令 hyb2 81.2 (v29c 91.7)
   与 big1 79.2 (87.5) 略低、0.08m 更激进会摔;
3. **v33d 已设为默认交付档**; v29c 保留回退 (hyb2 最稳), v32b 为台阶专精前身。

回答用户"越大越好么": 不是。我们实测: 恒定 lr 时 v31b/v31c 在 3-5M 后回落; 本次四段 lr
阶梯+课程变难+命令分布变宽同时满足, 20M 才持续涨。Go1 的 60M 属于不同任务/算法/步数定义,
不能直接类比; 若要继续, 建议同样方式续到 40M (lr 再降一档) 或改进任务分布, 而不是无脑堆步数。
